# Два домена «Бани Вятки» на REG.RU

`main` — единственный источник релиза. GitHub Actions проверяет PHP 8.3 и 8.5, собирает Vite с настроенным `VITE_YMAPS_KEY`, проверяет эту сборку браузером и сохраняет один публичный артефакт на 7 дней. Обе задачи выкладки скачивают его по одному ID. Приватные `lib.php` и `retry.php` берутся из того же коммита.

| Параметр | Основной сайт | Дополнительный сайт |
|---|---|---|
| Домен | banivyatki.ru | bani-vyatki.ru |
| Услуга и аккаунт | Хост-А, u3717330 | Хост-О, u3732869 |

## Однократная настройка Хост-О

1. В личном кабинете REG.RU откройте услугу «Хост-О» → данные доступа. В ISPmanager проверьте владельца сайта `u3732869`, сайт `bani-vyatki.ru`, PHP FastCGI 8.3, привязку SSL к сайту и его псевдониму `www`. При внешней проверке 20.11.2026 оба имени предъявили доверенный сертификат Let's Encrypt, действительный до 18.02.2027. На хостинге включите HTTP → HTTPS, если редирект ещё отсутствует. У основного сайта своя услуга.
2. Откройте файловый менеджер **именно этого сайта**. В его публичном корне рядом со стандартным `index.html` создайте `bv-host-u3732869.txt`. Запишите 32 случайных шестнадцатеричных символа в нижнем регистре, например результат `openssl rand -hex 16`. Файл общедоступный, содержит только эту строку. Откройте `https://bani-vyatki.ru/bv-host-u3732869.txt` и убедитесь, что видна та же строка. Оставьте файл на месте для последующих проверок. Маркер и файл состояния выкладки не входят в артефакт.
3. В FTPS-клиенте выберите **явный FTP поверх TLS**, порт 21, проверку доверенного сертификата и имени `server38.hosting.reg.ru`. Используйте логин и пароль этой услуги. Перейдите в каталог, прочитайте маркер и зафиксируйте реальный путь и ответ команды PWD. Скрипт принимает проверенную структуру `/www/<домен>`, полный путь этого аккаунта или `/<домен>` для FTP-пользователя, чей корень уже соответствует общему каталогу `www` и сверяет содержимое маркера по FTPS и HTTPS. Значение `REG_NEW_FTP_DIR` должно оканчиваться на `/`. Если FTP-пользователь изолирован в публичном корне сайта, выберите на Хост-О пользователя с доступом к общему родительскому каталогу сайта и приватного PHP, затем повторите проверку PWD и маркера. Пустая строка, FTP-корень или каталог первого сайта не подходят. Учётной записи нужны права на публичные файлы и **два файла кода** в соседнем `private`.
4. В `/var/www/u3732869/data/www/private/` установите `lib.php` и `retry.php` из согласованного коммита. Этот каталог должен находиться вне всех виртуальных хостов. Создайте в нём рабочий `config.php` защищённым способом на стороне хостинга по структуре `server/config.sample.php`. Используйте проверенные поля, источник, стадию и webhook существующей интеграции. Конфиг должен читаться веб-процессом и CLI-PHP. Доступ к конфигу ограничьте владельцем, если оба процесса работают от этого пользователя. Дайте обработчику права записи на его очереди, счётчики и журналы. На новом сервере начните с пустой очереди. Копирование очереди действующего сайта может повторно отправить обращения.
5. Проверьте PHP CLI на Хост-О через `php -v` и `php -m` у выбранного интерпретатора, расширения curl и mbstring, синтаксис обоих файлов и конфигурации через `php -l`. В ISPmanager → Планировщик добавьте отдельное задание каждые 5 минут с **проверенным полным путём CLI** и аргументом `/var/www/u3732869/data/www/private/retry.php`. Оба хостинга обслуживают собственные очереди. Переносить cron Хост-А с путём PHP 8.5 на Хост-О без проверки нельзя.
6. В GitHub → Settings → Secrets and variables → Actions внесите три секрета и две переменные из правого столбца. Укажите подтверждённый FTP-путь, сервер `server38.hosting.reg.ru` и режим `dry-run`. Пароли и webhook вводятся непосредственно в соответствующем кабинете. Общий `VITE_YMAPS_KEY` уже используется при сборке. Это браузерный ключ JavaScript API, он присутствует в JS по назначению. Проверьте разрешённые домены в кабинете Яндекс Карт, привязку нового домена и подмену номера в Callibri, учёт визитов в счётчике Метрики 113423850.

## Первый dry-run и согласование

В PR №59 запустите повтор задач Actions после сохранения переменных. Если задача второго сайта уже завершилась с `off`, повторите **весь запуск** или отдельно эту задачу, пока артефакт доступен. Смотрите выбранный режим в *Job summary*. PR допускает только чтение. Ветка этого аудита умеет проверять и основной сайт, когда его обычный режим на `main` равен `live`.

Успешный `dry-run` проверяет доверенный FTPS, PWD, привязку к HTTPS, контрольные суммы приватного кода и сравнивает публичные файлы с артефактом. В журнал выводятся имена отличающихся публичных файлов. Служебный заполнитель `photos/.gitkeep` исключён из выкладки настройками FTP-действия. Строка `absent or unreadable` включает код FTP 550. На пустом сайте большинство файлов ещё отсутствует. Режим не проверяет права записи. Отсутствие или неизвестная версия приватных файлов, неправильный маркер, каталог или сертификат останавливают задачу. `off` и пустое значение выключают этот хост. Другие значения считаются ошибкой.

После успешных проверок владелец отдельно согласует слияние в `main`. Слияние запускает существующий режим **обоих** сайтов: если у Хост-А стоит `live`, основной сайт обновится сразу. Для запуска Хост-О установите `REG_NEW_DEPLOY_MODE=live` после отдельного согласования. В Actions → **Build and deploy site to REG.RU** → **Run workflow** выберите `main` и снимите флаг **Read-only preflight on enabled targets**. Изменение переменной само по себе не запускает workflow. После этого обычные push в `main` автоматически обновляют каждый сайт с режимом `live`.

## Что делает live

- Перед записью каждый job сверяет SHA с текущей `main`. Для Хост-А он сравнивает байты `index.html` по FTPS и HTTPS. Для Хост-О обязательны ожидаемый сервер, каталог аккаунта и совпадение отдельного маркера по обоим протоколам.
- В соседнем `private` проверяются только `lib.php` и `retry.php`. Первичная сверка Хост-А с `1e659fc90264862223e08b9bfaccd90ff3dfe65a` выполнена в [журнале аудита](https://github.com/volkov43-beep/banivyatki-landing/actions/runs/44695375311/job/136150774285). Для обновления допускается совпадение с проверенной исходной версией либо версией файла из последующей истории `main` по первой родительской линии. Незнакомое содержимое останавливает выкладку до записи. Обновление сначала размещает и проверяет временные копии, затем переименовывает их по одной. Частично обновлённая пара может завершить обновление при повторном запуске. Изменения этих двух файлов и публичного обработчика должны допускать работу со смежной версией во время выкладки. Для config.php проверяется только наличие ненулевого размера. Содержимое конфига, журналов и очереди не читается и не синхронизируется.
- Публичный каталог обновляет прежний FTP-Deploy-Action v4.3.5, закреплённый по SHA, в режиме FTPS `strict` без полной очистки. Действие ведёт собственное состояние ранее опубликованных файлов. Никогда не добавляйте в публичное состояние файлы REG.RU, пользовательские данные или маркер хоста.
- После загрузки проверяются хеши публичных HTML, CSS, JS, картинок и robots по HTTPS, PHP и правил Apache по FTPS, точный JSON и статус 405 на GET обработчика, а также редирект www с сохранением пути и UTM. Это позволяет проверить исполнение PHP без создания заявки в рабочей CRM.

## Приёмка первого запуска

На каждом домене откройте `/`, `/syktyvkar/`, `/privacy/`, проверьте телефон и карты. Переходы внутри сайта и отправка `/api/lead.php` должны оставаться на текущем домене. Canonical и `og:url` главной и региональной страниц ведут на соответствующий URL `banivyatki.ru`, OG-изображение общее. Политика имеет `noindex`, `robots.txt` закрывает `/privacy/`. Основной домен каждого сайта остаётся самостоятельным, www переходит на свой домен.

После разрешения на контрольную заявку проверьте в Битрикс24 одну помеченную тестовую сделку на одно отправление. Сверьте адрес страницы, источник, UTM, регион, комплектацию и цену. Автотесты CI проводят восемь сценариев в браузере на каждом домене и в каждом регионе с локальным двойником CRM. Статус 200 от PHP возможен также при помещении заявки в очередь. Подтвердите работу cron и фактическую доставку перед запуском трафика. Синхронизация отправляет только код и контент. При неопределённом исходе запроса `crm.deal.add` после сетевого обрыва существующая интеграция не гарантирует строго однократное создание сделки.

## Восстановление после сбоя одного хостинга

Два сайта обновляются независимо. Ошибка любого включённого job оставляет весь запуск красным, другой job доходит до собственного результата. В сводке каждого указаны домен, режим, SHA и ID артефакта. Одновременная смена версии на двух серверах не гарантируется.

1. Если SHA по-прежнему последний в `main`, исправьте причину на неуспешном хосте. Нажмите **Re-run failed jobs**. Успешная публикация второго хоста при этом не повторяется, используется тот же артефакт.
2. Если `main` уже ушла вперёд или артефакт истёк, выполните **Run workflow** на текущей `main` для обоих включённых хостов. Не запускайте старый релиз поверх нового. Если проверка HTTPS выявила расхождение при корректном состоянии FTP, проверьте кеш хостинга и отличающийся публичный файл по SHA из проверенного артефакта. Устраните расхождение и повторите проверку до совпадения.
3. При неизвестном приватном PHP сопоставьте серверную копию с исходниками, сохраните отдельную защищённую резервную копию и согласуйте расхождение с владельцем. Затем восстановите согласованные версии только двух файлов. При необходимости отката выпустите новый revert-коммит в `main` обычным процессом. Очереди, журналы, конфиг и CRM не откатываются.
