# Зеркальная публикация двух доменов REG.RU через GitHub

## Назначение

- Единый исходный код: репозиторий `volkov43-beep/banivyatki-landing`, ветка `main`.
- Основной домен: `https://banivyatki.ru/` (REG.RU «Хост-А», аккаунт `u3717330`).
- Дополнительный домен: `https://bani-vyatki.ru/` (REG.RU «Хост-О», аккаунт `u3732869`).
- **Одна проверенная Vite-сборка `dist/` публикуется в обе отдельные папки сайтов.**
- Региональная страница `/syktyvkar/` и `/privacy/` входят в эту же сборку.
- Приватный PHP-конфиг с секретами CRM не попадает в GitHub и публичную папку.

## Состояние автоматики

Существующий workflow `.github/workflows/build-site-archive.yml` продолжает
публиковать основной домен через уже настроенные `REG_FTP_*`.
Для нового домена добавлен отдельный FTPS-шаг с собственными переменными.
Если новые переменные не настроены, публикация нового домена **выключена**,
а действующая публикация основного домена не меняется.

Ветки и PR запускают проверки и создают ZIP-артефакт `banivyatki-reg-ru-site`
(`dist/`), но **не публикуют в live**. На `main` публикация регулируется
значениями `REG_DEPLOY_MODE` и `REG_NEW_DEPLOY_MODE`.

## Однократная настройка нового хостинга

1. На REG.RU в «Хост-О» проверьте сайт `bani-vyatki.ru`: его корень
   `/var/www/u3732869/data/www/bani-vyatki.ru/` (в файловом менеджере
   `/www/bani-vyatki.ru/`). **Не путать с «Хост-А».**
2. Проверьте доверенный SSL Let's Encrypt для `bani-vyatki.ru` и
   `www.bani-vyatki.ru`, затем включите перенаправление HTTP → HTTPS
   через настройки сайта хостинга.
3. В разделе REG.RU «Доступы» получите адрес FTPS, логин и пароль
   нового хостинг-аккаунта (предпочтительно отдельный ограниченный пользователь).
   Подключение обязательно с проверкой TLS. Не передавайте доступы в чате.
4. Подключившись по FTPS, **проверьте реальный FTP-видимый путь** к папке
   `bani-vyatki.ru`. Пример `./www/bani-vyatki.ru/` допустим
   **только после проверки**. Файловый менеджер и FTPS могут показывать
   разные корневые пути.
5. GitHub → Settings → Secrets and variables → Actions → Secrets:
   создайте `REG_NEW_FTP_SERVER`, `REG_NEW_FTP_USERNAME`,
   `REG_NEW_FTP_PASSWORD`. Значения секретов не печатать.
6. Там же в Variables создайте:
   - `REG_NEW_FTP_DIR` — только проверенный FTPS-путь с завершающим `/`;
   - `REG_NEW_DEPLOY_MODE` — сначала `dry-run`, после проверки — `live`.
7. Выполните PR-проверки и dry-run. Сверьте, что фактический путь соответствует
   `bani-vyatki.ru` на **Хост-О**, а не действующему сайту.
8. После ревью объедините PR с `main`; убедитесь, что основной сайт успешно
   обновляется без изменения своих секретов. На первом прогоне
   `REG_NEW_DEPLOY_MODE=dry-run` ничего не запишет на Хост-О.
9. Только после успешного dry-run установите `REG_NEW_DEPLOY_MODE=live`
   и запустите workflow с `main` (или дождитесь следующего изменения).
   Изменения в `main` далее публикуются на обоих сайтах автоматически.

Workflow использует `SamKirkland/FTP-Deploy-Action@v4.3.5` по FTPS с
`security: strict`, не выполняет опасную полную очистку каталога.

## Что передаётся в публичную директорию

`dist/index.html`, `dist/asset(s)/`, `dist/photos/`, `dist/robots.txt`,
`dist/.htaccess`, `dist/privacy/`, `dist/syktyvkar/`,
`dist/api/lead.php` и другие файлы `dist/`.

Не загружать исходный ZIP из кнопки GitHub «Download ZIP» прямо в веб-каталог:
`src/`, `.github/`, `server/`, `node_modules/`, `.env` в публичном
корне не нужны и недопустимы.

## Приватная серверная часть

На новом хостинге **однократно** требуется создать `www/private/`
(соседнюю к `www/bani-vyatki.ru/`, но не внутри неё). В ней находятся:

- `lib.php` — копия `server/lib.php`;
- `retry.php` — копия `server/retry.php`;
- `config.php` — отдельная защищённая настройка, **не из репозитория**:
  webhook и коды полей CRM, без публикации значений;
- `queue/` и журналы для повторных отправок.

Проверить разрешения, синтаксис PHP под версией хостинга, работу нового
`/api/lead.php` и фактическое создание сделки в Битрикс24.
После проверки интеграции создать cron для `retry.php` по интерпретатору,
который действительно есть на «Хост-О».

**Ограничение текущего workflow:** `server/lib.php` и `server/retry.php`
не входят в `dist/` и пока не обновляются автоматически.
Требуется отдельный безопасный FTPS job для синхронизации этих двух файлов,
который никогда не переписывает `private/config.php` или `queue/`.
До его включения изменения в приватной библиотеке надо переносить и
проверять отдельно, иначе backend двух сайтов может разойтись.

## SEO и редиректы

Основной индексируемый адрес остаётся `banivyatki.ru`. Canonical,
Open Graph и `robots.txt` продолжают указывать на основной домен:
так не создаётся конкурирующий дубликат сайта для поисковиков.
`www.bani-vyatki.ru` перенаправляется на `bani-vyatki.ru`.
Домен `bani-vyatki.ru` **не переадресуется** на основной: оба доступны
посетителям и показывают одинаковую сборку.

## Проверка выпуска

Для каждого сайта проверить:
- главную, `/privacy/` и `/syktyvkar/`;
- сертификат HTTPS, оба варианта www;
- 200 для HTML/CSS/JS и изображений, отсутствие ошибок консоли;
- калькулятор, каталог, квиз и поведение на мобильном устройстве;
- заявки каждого сценария, статус API и появление сделок/контактов в CRM;
- повторные попытки и очередь, права доступа к приватным файлам;
- внешний `/private/config.php` не должен быть доступен по HTTP.

Не включать рекламный трафик на дополнительном домене до проверки CRM.
